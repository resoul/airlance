# messenger

Бэкенд мессенджера на Go. Архитектура вдохновлена MTProto: Noise IK на транспорте,
FlatBuffers как wire-протокол. Первая фаза — сервер + iOS/macOS клиенты.

## Требования

- **Go** 1.22+
- **flatc** (FlatBuffers compiler) — версия, использованная при разработке этого
  репозитория:

  ```
  flatc version 2.0.8
  ```

  Кодген может отличаться между мажорными версиями `flatc`. Если ставишь через
  `brew install flatbuffers` на macOS — скорее всего получишь более новую версию
  (24.x+). Перед первым `make gen` **сверь вывод `flatc --version` с указанным
  выше** и при расхождении — либо зафиксируй ту же версию через явную установку
  (`brew install flatbuffers@2` или сборка из исходников тега `v2.0.8`), либо
  прогони `make gen` и убедись, что сгенерированный код не сломал `go test ./...`
  прежде чем обновлять эту версию в README.
- Если планируется Linux CI — убедиться, что та же версия `flatc` доступна там
  (Docker image или сборка из исходников), чтобы кодген в CI не расходился с
  локальным.

## Генерация кода

Единственный способ обновить сгенерированный Go-код из `proto/schema.fbs`:

```bash
make gen
```

`internal/protocol/generated/` — артефакт сборки, не коммитится (см.
`.gitignore`). `make build` и `make run` сами зависят от `make gen`, так что
рассинхрон схемы и кодгена исключён при использовании `make`.

### Известный нюанс окружения: GOPROXY

Если `go mod tidy` / `go get` падает с `403 Forbidden: proxy.golang.org` (например,
сеть ограничена allowlist'ом без Go module proxy, но с доступом к `github.com`) —
используй:

```bash
GOPROXY=direct GOSUMDB=off go mod tidy
```

Это заставляет Go тянуть модули напрямую с VCS (GitHub), в обход
`proxy.golang.org`. `GOSUMDB=off` отключает проверку через `sum.golang.org`,
который по той же причине может быть недоступен. В доверенной сети (обычный
laptop/CI с полным доступом в интернет) это не нужно — обычный `go mod tidy`
работает как есть.

## union Body — правило неизменности порядка

FlatBuffers резолвит union-варианты по числовому индексу, **не по имени**.
Правила (продублировано из `proto/schema.fbs`, чтобы было видно без открытия
схемы):

1. Новые варианты добавлять **только в конец** списка.
2. Никогда не переставлять местами существующие варианты.
3. Никогда не удалять существующий вариант — старые клиенты могут прислать
   фрейм с этим индексом. Если вариант больше не нужен — оставить table
   как deprecated в комментарии, не убирать из union.
4. Один PR = один append.

Текущий зафиксированный порядок:

| Индекс | Вариант | Этап | Назначение |
|---|---|---|---|
| 0 | `NONE` | — | зарезервировано FlatBuffers |
| 1 | `Ping` | 5 (heartbeat) | keepalive, заведено заранее |
| 2 | `Pong` | 5 (heartbeat) | keepalive, заведено заранее |
| 3 | `NewSession` | 4 (session) | первое подключение с устройства после handshake |
| 4 | `ResumeSession` | 4 (session) | восстановление сессии после handshake |
| 5 | `RegisterAccount` | registration | запрос на регистрацию аккаунта (email, firstName, lastName) |
| 6 | `RegisterAccountAck` | registration | подтверждение регистрации (account_id) |
| 7 | `ConfirmEmailCode` | registration | подтверждение кода из email (account_id, code) |
| 8 | `ConfirmEmailCodeAck` | registration | результат подтверждения (session_id, device_id) |
| 9 | `Error` | general | единый фрейм ошибки протокола (code, message) |

`NewSession`/`ResumeSession` — application-фреймы, отправляемые **после**
завершения Noise IK handshake (Этап 3), не часть самого handshake payload.
Это осознанное архитектурное решение: транспортный/крипто-слой не должен знать
про существование сессий — это ответственность usecase-слоя (Message Router,
Этап 6). Handshake доказывает владение device key; `session_id` далее
используется только для поиска существующего контекста, не как секрет.

Нарушение правил порядка ломает wire-совместимость со всеми клиентами,
собранными до изменения. `TestUnionBodyIndicesAreStable` в
`internal/protocol/smoke_test.go` фиксирует текущие значения индексов —
если тест упал после правки схемы, скорее всего кто-то нарушил порядок.

## Этап 1 — транспортный слой (`internal/transport`)

Голый TCP + length-prefix framing, без какого-либо шифрования (Noise появится
на Этапе 3). Три файла:

- **`framing.go`** — `ReadFrame`/`WriteFrame` поверх `io.Reader`/`io.Writer`.
  4-байтовый big-endian length prefix, `MaxFrameSize = 1 MiB`. Размер
  проверяется **до** аллокации буфера под тело (см. `TestReadFrame_
  RejectsOversizedLengthPrefix_WithoutAllocating` — тест ловит именно этот
  случай, не только декларирует поведение в комментарии).
- **`connection.go`** — `Connection`, тонкая обёртка над `net.Conn` с
  **блокирующим** API: `ReadFrame() ([]byte, error)` / `WriteFrame([]byte)
  error`. Осознанно без внутреннего канала/горутины-ридера — вызывающий код
  сам решает свою конкурентную модель. Причина: Message Router (Этап 6) по
  плану сам оборачивает чтение в горутину+канал ("горутина на соединение
  читает фреймы → кладёт в канал → воркер-пул обрабатывает"); если бы
  `Connection` уже содержал канал внутри, получился бы двойной асинхронный
  слой без явной пользы, плюс тесты требовали бы `select{}`/таймауты вместо
  прямых синхронных вызовов.
- **`listener.go`** — `Listener.ListenAndServe()`, accept loop, горутина на
  соединение. `Handler` — это `func(conn *Connection)`, вызывается в
  отдельной горутине на каждый `Accept`, сам отвечает за свой цикл чтения и
  за `Close()`.

### Открытые вопросы, оставленные явно не решёнными на этом этапе

- **Graceful shutdown.** `ListenAndServe` сейчас блокируется до ошибки
  `Accept` (включая закрытие самого listener'а) и не умеет остановиться по
  сигналу/контексту. Осознанно не реализовано сейчас — форма API
  (`context.Context`? отдельный `Shutdown()` метод?) должна определяться
  реальным caller'ом, который появится вместе с Connection ID registry
  (Этап 4) или heartbeat/connection manager (Этап 5), а не гадаться заранее.
- **Паника внутри `Handler`.** `Listener` не делает `recover()` вокруг
  вызова `Handler` — паника в обработчике одного соединения уронит весь
  процесс. Это тоже осознанно отложено: стоит ли вообще глушить панику
  молча или это должно быть решением на уровне Message Router (который
  лучше знает семантику своих ошибок) — решится на Этапе 6.

## Серверный static keypair (`internal/identity`, `cmd/keygen`)

Из полного Этапа 2 плана ("Identity и ключи") на данный момент сделана
**только** часть, без которой не может стартовать Noise IK handshake (Этап
3): статический X25519 keypair сервера.

**Осознанно НЕ сделано сейчас** (отложено до отдельного этапа регистрации
пользователей, после того как транспорт+крипто будут стабильны):
- HTTP/gRPC endpoint регистрации устройства
- PostgreSQL-схема `accounts`/`devices`
- Привязка device key → account/device ID

Причина: фокус сейчас на бэкенде и транспортном/крипто-слое, без перехода на
клиентскую часть. PKI пользователей — это в первую очередь про регистрацию
живых людей (email/phone/OTP и т.п.), которая как продуктовая фича будет
проектироваться отдельно, а не как побочный довесок к Noise-хендшейку.

### Как это устроено

- **`internal/identity/serverkey.go`** — `GenerateServerKeyPair`,
  `SaveServerKeyPair`, `LoadServerKeyPair`. Использует `crypto/ecdh`
  (стандартная библиотека Go 1.20+, `ecdh.X25519()`) — без внешних
  crypto-зависимостей.
- Формат файла — JSON с явным `version` (формата файла, не путать с
  версией/ротацией самого ключа) и `key_id`. `key_id` заведён с самого
  начала, а не добавлен при ротации отдельной миграцией — под будущую
  поддержку нескольких pinned-ключей на клиенте.
- Приватный ключ на диске хранится с правами **0600**, `SaveServerKeyPair`
  принудительно выставляет их даже поверх уже существующего файла с более
  широкими правами.
- `LoadServerKeyPair` пересчитывает публичный ключ из приватного и сверяет
  с сохранённым `public_key_hex` — ловит повреждение файла.

### Генерация ключа

```bash
go run ./cmd/keygen -key-id=v1 -out=server-key.json
```

`cmd/server` **не генерирует ключ сам**, если файла нет — это осознанное
решение: генерация приватного ключа сервера должна быть явным действием
оператора, не побочным эффектом обычного запуска (иначе есть риск случайно
создать новый ключ при неправильно настроенном пути на деплое и молча
разорвать pinning со всеми уже собранными клиентами). `keygen` по умолчанию
отказывается перезаписывать существующий файл — нужен явный `-force`.

## Этап 3 — Noise IK handshake (`internal/noiseik`)

`Noise_IK_25519_ChaChaPoly_SHA256` через `github.com/flynn/noise`. Два файла:

- **`noiseik.go`** — `ClientHandshake`/`ServerHandshake`: выполняют
  handshake поверх уже установленного `transport.Connection` (сырые
  handshake-сообщения идут через его `Read/WriteFrame`, framing/лимит
  размера Этапа 1 переиспользуется как есть, отдельного механизма под них
  не заводилось). Оба возвращают `*Conn` при успехе.
- **`conn.go`** — `Conn`: тот же блокирующий `ReadFrame`/`WriteFrame` API,
  что и у `transport.Connection`, но прозрачно шифрует/расшифровывает
  каждый фрейм. Верхний код (сейчас — демо Ping/Pong в `cmd/server`, позже
  — Message Router Этапа 6) работает с `Conn` так же, как раньше работал бы
  с голым `Connection`, ничего не зная про Noise.

`Conn.RemoteStaticKey()` — статический публичный ключ собеседника,
подтверждённый handshake'ом (для сервера — device key клиента). Это ровно
то, на чём будет строиться регистрация устройств: сервер узнаёт публичный
ключ клиента с доказательством владения прямо из handshake, без отдельного
HTTP-эндпоинта и без пересылки сырого pubkey отдельным пакетом данных —
см. обсуждение флоу email-регистрации в проектных заметках. **Сервер
осознанно не проверяет и не ограничивает, чей именно static key ему
предъявляют** — это решение application-слоя (регистрация/резюм сессии)
поверх уже установленного зашифрованного канала, не крипто-слоя.

### Осознанно отложено на этом этапе

- **0-RTT/payload в handshake-сообщениях.** Оба `WriteMessage` вызываются с
  `payload=nil`. 0-RTT данные в Noise не защищены от replay без отдельного
  механизма — не тащим эту сложность, пока нет конкретной причины слать
  что-то до завершения handshake.
- **Версионирование/ротация серверного ключа на уровне самого handshake.**
  Сейчас клиент обязан точно знать текущий pinned publicKey; выбор `key_id`
  при нескольких актуальных ключах в Noise-сообщениях не передаётся. При
  ротации потребуется отдельный механизм (например, plaintext-префикс перед
  Noise-сообщениями с `key_id`) — не решается заранее, пока ключ один (v1).
- **Интеграция с Message Router / Session (Этап 4).** `Conn` пока
  используется только для демо Ping/Pong в `cmd/server`; `NewSession`/
  `ResumeSession` фреймы (уже зарезервированные в `schema.fbs`) ещё не
  обрабатываются нигде.

### Тесты (`noiseik_test.go`)

- `TestHandshake_RoundTrip` — happy path: handshake с обеих сторон,
  корректный `RemoteStaticKey()`, шифрованный обмен фреймами в обе стороны.
- `TestHandshake_WrongPinnedServerKeyFails` — клиент "закрепил" не тот
  публичный ключ сервера (симуляция MITM/неверного pinning'а на билде) —
  handshake обязан провалиться на обеих сторонах до первого application-
  фрейма. Это тест, явно требовавшийся в исходном плане Этапа 3.
- `TestSession_TamperedFrameFailsAuthentication` — изменение одного байта
  шифртекста ловится AEAD-тегом при расшифровке.

### Зависимость

Добавлена `github.com/flynn/noise` в `go.mod`. `go.sum` под неё **не
заполнен** — нужно прогнать `go mod tidy` локально (см. раздел про GOPROXY
выше, если сеть ограничена allowlist'ом без `proxy.golang.org`) прежде чем
`make build`/`make test` заработают.

## Команды

```bash
make gen                 # сгенерировать Go-код из proto/schema.fbs
make build               # gen + go build ./...
make test                # gen + go test ./...
make run                 # gen + запуск сервера (go run ./cmd/app serve)

# Запуск CLI команд приложения
go run ./cmd/app keygen --key-id=v1 --out=server-key.json
go run ./cmd/app serve --addr=:8080 --key=server-key.json
go run ./cmd/app migrate up --dsn="postgres://postgres:postgres@localhost:5432/messenger?sslmode=disable"
go run ./cmd/app migrate down --steps=1
```

## Конфигурация (.env)

Приложение поддерживает загрузку переменных окружения через `.env` файл или `ENV` переменные (`github.com/joho/godotenv` + `github.com/kelseyhightower/envconfig`):

| Переменная | По умолчанию | Описание |
|---|---|---|
| `APP_ENV` | `development` | Окружение приложения (`development`, `production`). В `production` логгер выводит JSON. |
| `LOG_LEVEL` | `info` | Уровень логирования (`debug`, `info`, `warn`, `error`). |
| `SERVER_ADDR` | `:8080` | TCP порт/адрес прослушивания сервера. |
| `SERVER_KEY_PATH` | `server-key.json` | Путь к файлу статического X25519 ключа сервера. |
| `HEARTBEAT_TIMEOUT` | `60s` | Таймаут молчания сокета клиентских соединений. |
| `DB_DSN` | `postgres://postgres:postgres@localhost:5432/messenger?sslmode=disable` | Строка подключения к PostgreSQL. |
